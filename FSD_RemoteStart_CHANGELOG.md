# FSD changelog — Remote Start System

The development record for `FSD_RemoteStart.md`. Every change to the
specification lands here, newest first.

The two files have different jobs. **`FSD_RemoteStart.md` is the clean current
specification**: what the system is required to do, in the present tense, with
no history in it. **This file is how it got that way** — what changed at each
version, and more importantly *why*, so a decision that looks arbitrary later
can be traced back to the evidence that forced it.

Read the FSD to build the thing. Read this when you want to know why it says
what it says, or before reopening a question that was already settled. This
project is the origin of the house conventions the sibling projects inherit —
the provisioning portal, the tab layout, the OTA flow — so several entries here
are cited by name in those projects' specifications.

Entry format: `- vX.Y — **Title.** what + why + how`, with per-unit firmware
versions named where they changed (MasterRemote, SlaveHonda, SlaveWallas,
ESPNowRelay). A functional change is not done until the code, the unit version
bumps, and an entry here land together.

---

- v1.54 — **Browser flasher for a new unit, on GitHub Pages** (§11.1). A new board can now be flashed from https://sespe.github.io/RemoteStart/ in Chrome or Edge, with no ESP-IDF or esptool on that computer — the same esp-web-tools pattern as the BirdBox project, extended to four units on two chip families. CI/docs only — no firmware, endpoint or NVS change, and no unit version bump.
  - **New `.github/workflows/webflash-pages.yml`:** on a push to `master` that touches a unit or the flasher, builds all four units in a matrix and deploys each one's bootloader, partition table, OTA data and app image plus a per-unit `manifest.json` to Pages. One `docs/webflash/manifest.template.json` serves all four; the matrix fills in the unit, `FIRMWARE_VERSION`, chip family and **bootloader offset, which differs by chip — 0x1000 on ESP32, 0x0 on ESP32-C6** (read from each unit's `flasher_args.json`). Getting that wrong would write a C6 bootloader where the ROM never looks.
  - **Per-unit buttons, not one:** the four units are four different firmwares, so the page has one install button per unit. esp-web-tools refuses a chip-family mismatch, so the C6 units are protected against the wrong board; MasterRemote and SlaveHonda share the ESP32 family and cannot be told apart, which the page warns about.
  - **Erase is offered by default** (`new_install_prompt_erase`), because a plain flash onto a board with unknown history once left a new MasterRemote's radio silent while its logs reported a running SoftAP.
  - **Fixed the release notes' USB instructions:** they told the reader to `write_flash 0x10000 <Unit>_<ver>.bin` alone, which on a blank board leaves no bootloader or partition table and does not boot. They now point at the browser flasher or `idf.py erase-flash flash`, and say the release `.bin` files are OTA app images. §8 says the same.
  - `README.md` "Build & Flash" now leads with the browser flasher.

- v1.52 — **Hardware documentation: new [docs/HARDWARE.md](docs/HARDWARE.md) plus the three source drawings under `docs/hardware/`.** Documentation only — no firmware, endpoint or NVS change, and no unit version bump. Covers MasterRemote's opto-isolated Venus (Raspberry Pi) interface board, the manual-switch/indicator field wiring and terminal-block assignments, the end-to-end Honda start flow through to the EU7000is remote connector, and the relay timing.
  - **Corrected §2.2: GPIO15 (Honda Start, Victron relay) is active LOW, not active HIGH.** The table had claimed active HIGH since v1.14 while `main.c` has always read it as `!gpio_get_level(PIN_HONDA_START)`. The schematic settles it — GPIO15 is fed by optocoupler U1's open collector with an external 10 kΩ pull-up, and the internal pull-up is disabled in `gpio_init()`. Confirmed live on 2026-08-10: with the system idle, `/api/gpio/status` reports GPIO15 = 1 and GPIO4 = 1, which is only possible with external pull-ups fitted, and `/api/status` correspondingly reads `pHS:false`/`pWS:false`. Both Victron inputs use the same polarity; the old text's "opposite polarity of GPIO15" note on the GPIO4 row was wrong for the same reason and is removed. No code changed — the firmware was already correct, only the document was not.
  - The **redrawn** schematic (`MasterRemote_interface_schematic.png`) was found to contain five transcription errors relative to the hand-marked original, catalogued in Hardware Guide §6 — most consequentially a right-header pin-label list with `23` and `15` duplicated and `5`/`2` missing, which shifts every row from the third down and makes the Wallas opto appear to land on GPIO16 rather than GPIO4. The marked original photo is kept alongside it and is the one to wire from until the redraw is fixed.

- v1.50 — **Two fixes to v1.49's version table, both reported from the live UI.**
  - **MasterRemote showed no versions for the slaves.** v1.49 had the page fetch `/api/version` from each slave's own address; a browser treats `http://<slave-ip>/` as a different origin from the page it loaded off MasterRemote, and those reads came back empty in practice even with `Access-Control-Allow-Origin: *` on the response. Replaced by **`GET /api/versions[?relay=<ip>]` on MasterRemote**, which collects the other units' `/api/version` itself over plain LAN HTTP (4 s timeout each, so one silent unit can't stall the table) and returns all four rows to a same-origin caller. Slave addresses still come from the ESP-NOW roster; ESPNowRelay's is still typed once into the card and kept in the browser, now passed through as a query parameter (validated against an IPv4 alphabet before it goes into a URL). `/api/version` stays on every unit — it is the data source, and still CORS-open for direct use.
  - **24-hour clock everywhere.** `new Date().toLocaleTimeString()` follows the viewing browser's locale and was rendering as `7:43:39 PM`. All UI timestamps (Status/Nodes "Updated:", the version card) now go through one `hms()` helper producing zero-padded `HH:MM:SS`, on all four units.
  - Also: a stored version read from a pre-v1.49 image is a `git describe` string that already starts with `v`, which rendered as `vv1.31.0`; the leading `v` is now stripped before the display prefix is added.
  MasterRemote 1.6.14, SlaveHonda 1.4.12, SlaveWallas 1.6.12, ESPNowRelay 1.1.11.
- v1.49 — **Firmware Versions table on the OTA tab: GitHub / Stored / Installed side by side, on all four units** (§6.6, §7.3). Each unit's OTA tab now opens with a version card showing what the newest published release offers for it (**GitHub**), what sits in its inactive OTA slot (**Stored** — the previous image, still bootable), and what it is running (**Installed**); the Installed box turns amber when GitHub has a newer build. **MasterRemote's card lists all four units in one table**, like the reference layout the feature was modelled on.
  - **New `GET /api/version`** on every unit: `{"name","installed","stored","storedName","running"}`. `stored` comes from `esp_ota_get_partition_description()` on `esp_ota_get_next_update_partition()`, and is empty when that slot has never been written or holds no valid image. Served with `Access-Control-Allow-Origin: *` on purpose — MasterRemote's page fetches this same endpoint from the other units' addresses, which is cross-origin from the browser's point of view; the payload is read-only version data on a LAN-only device.
  - **New `GET /api/ota/github/latest`** on every unit: the newest published version per unit, `{"MasterRemote":"…","SlaveHonda":"…","SlaveWallas":"…","ESPNowRelay":"…"}`, parsed out of the `<Unit>_v<ver>.bin` asset filenames. Reuses v1.48's streaming scanner (never materialises the listing) and captures only `browser_download_url`, stopping as soon as all four are known — normally inside the first release, since a unified `v*` tag carries all four bins. All four firmwares carry the identical four-unit handler even though only MasterRemote's page reads more than its own key.
  - **`PROJECT_VER` is now derived from `main/version.h` in each unit's top-level `CMakeLists.txt`**, so the app descriptor baked into the image carries `FIRMWARE_VERSION`. Without this, ESP-IDF fills the descriptor from `git describe`, which says nothing about the per-unit firmware version — and the descriptor is the only way to read a *passive* partition's version. **Consequence on first deploy: the Stored column shows a `git describe`-style string (or blank) until each unit has been updated twice**, since the image already in the passive slot predates this change.
  - **How MasterRemote resolves the other three addresses:** SlaveHonda and SlaveWallas come from `/api/nodes` (so the table follows a DHCP move), while **ESPNowRelay is deliberately absent from the ESP-NOW roster** — the repeater is transparent and never announces itself (§13) — so its address is typed once into a field on the card and kept in the browser's `localStorage`. That was chosen over adding a relay→Master ESP-NOW message type purely to feed a display, since the repeater's whole design premise is that it changes nothing about the other units' firmware. A blank or unreachable address just leaves that row's cells empty; per-unit fetches are abort-timeout bounded so one silent unit can't stall the table.
  - ESPNowRelay's `max_uri_handlers` raised 16 → 20 for the two new routes (the other three units already had margin).
  MasterRemote 1.6.13, SlaveHonda 1.4.11, SlaveWallas 1.6.11, ESPNowRelay 1.1.10. No NVS, data-model, or wire-format change.
- v1.48 — **Two independent defects were breaking the GitHub-release OTA feature; both are fixed, plus a "Go GitHub" link and MasterRemote's missing Manual GPIO Test card.** User reported the feature not working on all units. Probing SlaveHonda live separated it into two unrelated causes that had been mistaken for one:
  - **(1) Release listing ran out of heap.** `GET /api/ota/github/releases` buffered the whole API response and handed it to `cJSON`. Each published release carries four per-unit assets of ~20 JSON fields, so the listing had grown past **68 KB**, and a full parse needs the raw buffer plus a tree several times its size against a ~200 KB heap. MasterRemote failed **3/3** with `Bad GitHub response` (the `cJSON_Parse()` branch — the malloc succeeded, the parse then had nothing left), its heap low-water plunging ~98 KB per attempt, while SlaveHonda with a little more headroom still squeaked through **9/9**. That difference is why it looked intermittent. Rewritten as a **byte-at-a-time streaming scanner** (`gh_key_feed()`) that never materialises the document: it watches for four literal keys, exploiting GitHub's field order (`tag_name`/`published_at` precede a release's `assets`; within an asset `size` precedes `browser_download_url`), takes the asset filename from the URL's own last path segment, and dedupes by tag so one asset per release is emitted. Peak cost no longer depends on the release count — which matters because the payload grows with every release, so trimming `per_page` would only have postponed this. Output JSON is byte-identical to the old implementation (verified live: same 1348 bytes, same 7 releases). Also now tolerates a chunked response, since the scanner no longer needs `Content-Length`, and a non-200 reply reports the actual status code instead of a generic string.
  - **(2) Outbound TLS could not get a socket.** With the listing fixed, `POST /api/ota/github/install` still failed instantly with `begin:ESP_ERR_HTTP_CONNECT`, trace `le=32770` = `0x8002` = **`ESP_ERR_ESP_TLS_CANNOT_CREATE_SOCKET`** — `socket()` itself failing, nothing to do with TLS or the buffer sizes v1.46 fixed. `CONFIG_LWIP_MAX_SOCKETS` was **10**, while httpd holds a listener, a control socket, and up to 7 sessions = 9, leaving exactly **one** descriptor for everything else. A browser parked on a polling tab fills all 7 session slots (they are keep-alive and `lru_purge_enable` only reclaims one when a *new* connection needs it, so an idle wait does not help — confirmed: still failing after 60 s quiet), so the device had no descriptor left to open its own outbound connection. Proven by a discriminating test: after a reboot with no preceding traffic the identical install ran **0%→100% success**. Fixed by raising `CONFIG_LWIP_MAX_SOCKETS` to **16** in all four `sdkconfig.defaults`, and `cfg.max_open_sockets` is now set explicitly with a comment recording that it is one half of a budget, so a future change to either number is visibly a trade against the other. This affected *both* the listing fetch and the install, so it was very likely also a contributor to the user-visible "Refresh Releases doesn't work".
  - **(3) "Go GitHub" link** added beside Refresh Releases on every unit's OTA tab, opening `github.com/SEspe/RemoteStart` in a new tab (`rel="noopener"`). Styled via a new `a.up.gh-link` rule because the existing `button.up` selector is element-qualified and gives an `<a>` none of its padding or colour.
  - **(4) MasterRemote gained the Manual GPIO Test card** its Debug tab was missing (the other three units had it since v1.40). Same pin matrix, same reserved-pin rules, same `/api/gpio/set` + `/api/gpio/status` endpoints. **One difference is called out in its UI and worth knowing:** unlike the slaves, whose drivable pins are their own relay outputs, MasterRemote's Victron-relay and manual-switch pins are *inputs fed by external contacts* (§2) — the strapping-pin rules already exclude GPIO5/GPIO15, leaving **GPIO4 and GPIO14** as pins where forcing OUTPUT puts the pad in contention with the external wiring. Reading their dots is always safe; driving them is not, unless that wiring is disconnected. `cfg.max_uri_handlers` raised 22→28, since the two new routes brought the count to exactly 22 — the exact-fit cap that silently dropped a route in v1.27/§12.
  MasterRemote 1.6.12, SlaveHonda 1.4.10, SlaveWallas 1.6.10, ESPNowRelay 1.1.9. New routes on MasterRemote only; no NVS, data-model, or wire-format change.
- v1.47 — **The WiFi tab now states the configured WiFi network and the addressing actually in use, on all four units.** Two gaps: (1) a unit's provisioned SSID was written to NVS at setup and then never shown anywhere in the UI — the WiFi tab's SSID box sat empty with a `tap network or type` placeholder, so the only way to tell which network a unit was on was to read it off the router; (2) the IP Configuration card's live readout omitted both the address *source* and the DNS server, so a `192.168.1.101` on screen didn't say whether it was the static address configured on this unit or a lease the router happened to hand out — a meaningful distinction now that all four units are statically addressed (§10.2). The **WiFi Network** card gains a live grid above the form with **Configured SSID** and **Connected To** rows, and the SSID input is now pre-filled with the configured value when empty (same prefill-don't-overwrite convention as v1.38's static-IP fields — a password-only change no longer means retyping the SSID). Switching to Static now also pre-fills the DNS field from the live value, completing the v1.38 prefill set (live DNS wasn't available to the UI before this change). `GET /api/ipconfig` gains `ssid`, `apSsid`, and `liveDns`; response buffer grown 400→600 bytes to fit two 32-char SSIDs. SSID JSON escaping (quote/backslash/control-char handling, previously inline in `/api/scan`) is factored into one `ssid_json_esc()` helper per unit and shared by both endpoints. MasterRemote 1.6.10, SlaveHonda 1.4.8, SlaveWallas 1.6.8, ESPNowRelay 1.1.7; endpoint-response-additive only, no NVS, data-model, or wire-format change.
- v1.46 — **Fixed v1.45's GitHub-releases install actually failing on real hardware** (`begin:ESP_FAIL` immediately, 0%, on every unit) — the feature was built, deployed, and its release-listing worked, but the install step itself was broken until now. Root cause, found live via a new HTTP-event trace (added specifically because there's no USB/serial access to these units in normal operation): GitHub's release-asset redirect target is a **signed URL around 2 KB long** (JWT query params via `release-assets.githubusercontent.com`). `esp_http_client` builds the outgoing `GET <path>?<query> HTTP/1.1` request line for the redirected request into `buffer_size_tx`, a **separate TX buffer from `buffer_size`** (which is RX-only) that still defaulted to 512 bytes even after `buffer_size` had already been bumped to 4096 for the RX side — the oversized request line silently failed with "Out of buffer" (an `esp_http_client`-internal `ESP_LOGE`, invisible without serial access) and `esp_https_ota_begin()` surfaced it as a bare `ESP_FAIL` with no further detail. Fixed by also setting `buffer_size_tx = 4096` on the OTA download's `esp_http_client_config_t`. Verified live end-to-end on ESPNowRelay before rolling out to the other three: release list fetched, install progressed 0%→95% as real percentages, device rebooted cleanly onto the new image. **New permanent diagnostic: an HTTP-event trace** (`gh_http_event_handler`, connect/redirect/status/data-chunk/error events, including decoded `esp_tls_last_error_t` fields on `HTTP_EVENT_ERROR`) is now wired into the GitHub-install client on all four units and exposed as a `trace` field on `GET /api/ota/github/progress` — kept intentionally (not stripped after the fix) since it's what made this diagnosable at all without USB access, and the failure mode (a CDN changing its redirect URL shape) could plausibly recur. New `esp-tls` component added to all four units' `CMakeLists.txt REQUIRES` for `esp_tls_last_error_t`. MasterRemote 1.6.9, SlaveHonda 1.4.7, SlaveWallas 1.6.7, ESPNowRelay 1.1.6; no data-model or wire-format change, endpoint-response-additive only (`trace` field).

- v1.44 — **The Wallas Manual switch on MasterRemote was physically reconnected, reversing the v1.29 "permanently unwired" status.** Confirmed live via `/api/status` with the switch in its "Off" position: `pWM` (the pre-existing, then-meaningless diagnostic field, formula `!gpio_get_level(GPIO5)`) read `true`, meaning the **raw pin is LOW when Off** — i.e. this switch is **non-inverted/active-HIGH** (On demands start), the *opposite* of GPIO4's active-LOW Victron relay input, but the *same* convention as GPIO14's Honda manual switch (which is also read non-inverted): both apparently ground their pin in the idle/off position and float pulled-up HIGH when active. An initial version of this change wrongly assumed GPIO5 would mirror GPIO4's active-LOW polarity by analogy — caught before OTA deploy by checking live `/api/status` first, which is why every hardware-polarity assumption in this codebase gets a "verify against the physical unit" callout (§12). Fixed to read `gpio_get_level(PIN_WALLAS_MANUAL_START)` directly, matching `PIN_HONDA_MANUAL_START`'s pattern. This is a **maintained on/off toggle**, not momentary, and OR's in as a plain level source alongside the Victron relay, web override, and weekly timer: On continuously demands Wallas start, Off just stops contributing to the OR (another source can still keep Wallas running). Restored across all four recompute sites (`isr_wallas_recompute`, `gpio_init()`'s boot-time read, `timer_task`, `h_wallas_stop`) and re-attached its ISR handler, per the §12 OR-recompute rule. `/api/status`'s `pWM` field also flipped to non-inverted to match the corrected command logic; UI label dropped "unused". MasterRemote-only (1.6.6); no data-model or wire-format change. **Not yet verified against the physical switch's On position** — confirm `gWS`/`pWM` flip correctly and the physical relay engages before relying on it.

- v1.39 — Added a **Last WiFi Reconnect** field next to the existing WiFi Reconnects counter on `/api/sysinfo`'s System card, all four units. - v1.14 — Renamed the master unit from **MasterHonda** to **MasterRemote** throughout: project directory (`MasterHonda/` → `MasterRemote/`, git history preserved via `git mv`), `FIRMWARE_NAME`, config-portal AP SSID (`MasterRemote-Config`), CMake project name, HTML page title/header, and every mention in this document, the README, and CI workflow. `NVS_NAMESPACE` was deliberately left as `"mhonda"` so the already-deployed unit keeps its stored WiFi credentials across the update. **Breaking change**: the discovery beacon's identity string changed length (`"MasterHonda"` = 11 chars → `"MasterRemote"` = 12 chars) and both slaves' `strncmp()` match against it — all three units must be reflashed together, or SlaveHonda/SlaveWallas will stop recognizing the beacon and lose discovery. Historical changelog entries below still say "MasterHonda" for the versions where that was the current name.
- v1.13 — Reorganized releases: introduced a release-level version, independent of each unit's own `FIRMWARE_VERSION` (which keep incrementing independently per unit, unchanged by this reorg). All three units are now released together under one combined git tag/GitHub Release at the release version (e.g. `v1.5.0`) instead of separate `master-v*`/`honda-v*`/`wallas-v*` tags — the CI workflow already supported this (a `v*` tag builds all three and attaches all three `.bin` files, each still named with its own unit's version, to one GitHub Release); the per-unit tag patterns just hadn't been in active use this session. Per-unit tags remain available in CI for a genuine single-unit hotfix, but `v*` is now the standard release path. See §8.
- v1.12 — SlaveHonda gains a Debug GPIO tab, mirroring SlaveWallas's (same `GET /api/gpio/set`/`GET /api/gpio/status` design), adapted for the ESP32-classic pin map: manipulable subset is GPIO 4,13,14,16-19,21-23,25-27,32,33; reserved-and-status-only covers strapping (0,2,5,12,15), embedded flash (6-11), UART0 console (1,3), and input-only pins (34-39). Status dots cover the full GPIO 0-39 range. SlaveWallas's regular Status tab gains a lamp-style row for the GPIO23 heater indicator LED (was previously only visible via the Debug tab, not the normal status view).
- v1.11 — SlaveWallas Debug GPIO tab now shows a live status dot (green = HIGH) for every GPIO 0-30, not just the manipulable subset, via a new read-only `GET /api/gpio/status`. Reserved pins (strapping, USB-JTAG) show status only, no ON/OFF buttons, since `gpio_get_level()` alone is passive (just reads the input register) and safe to call on any pin, unlike `h_gpio_set`'s active reconfiguration.
- v1.10 — SlaveWallas: the onboard status LED (GPIO2) blink speed is now keyed off `g_start_cmd` (start commanded by Master) instead of `g_wallas_running` (the running-feedback sensor on GPIO18) — the feedback sensor isn't wired up on this unit yet, so blink speed previously couldn't reflect anything meaningful.
- v1.9 — SlaveWallas: corrected heater relay pin, GPIO16 → GPIO19 (matches actual wiring, confirmed via the Debug GPIO tab added in v1.8). GPIO2 confirmed as the onboard status/heartbeat LED (blinks by design — slow when idle, fast when the heater is running; no change needed there).
- v1.8 — SlaveWallas: corrected stale pin labels on the Status tab (relay was still labeled "p0" after the GPIO0→16 move, feedback still labeled "p13" after the GPIO13→18 move — display-only, the underlying GPIO defines were already correct). Added a **Debug GPIO** tab: `GET /api/gpio/set?pin=N&level=0|1` reconfigures any non-reserved GPIO (0,1,2,3,6,7,10,11,14,16-23; strapping pins 4/5/8/9/15 and USB-JTAG 12/13 excluded) to OUTPUT and drives it, for hardware bring-up when physical pin wiring is uncertain. Overrides normal operation of that pin until reboot — hardware debug only, not for production use.
- v1.7 — Fixed a heap buffer overflow in `h_root()` on all three units: the `%IP%` template placeholder (4 chars) was replaced in-place via `memmove`/`memcpy` inside a buffer sized only for the original template (`strdup()`), so any IP string longer than 4 characters (i.e. almost any real IP) overflowed the allocation, corrupting the heap and crashing the device shortly after — usually visible as the TCP connection to `/` resetting mid-response, while smaller endpoints like `/api/status` kept working fine. Rewritten to build the substituted page into a freshly, exactly-sized buffer instead of mutating a fixed-size one in place. Discovered because SlaveHonda's root page happened to work (no WiFi IP → 1-char `"?"` placeholder, which shrinks rather than overflows) while SlaveWallas's (a real IP) reliably crashed on load.
- v1.6 — Slave heartbeats (`slave_msg_t`/`slave_wallas_msg_t`) now carry per-link RSSI, channel, and firmware version, sourced from the receiving radio's `rx_ctrl` on the last frame heard from MasterRemote (works whether or not the slave has its own WiFi/AP association). MasterRemote's Nodes tab is redesigned as a table (one row per node, RSSI/Channel/FW columns) instead of stacked cards, and the Pin Status tab gains manual **Start/Stop Honda** and **Start/Stop Wallas** buttons — a third command source OR'd in alongside the Victron relay and physical manual buttons via new `/api/honda/start\|stop` and `/api/wallas/start\|stop` endpoints. **Breaking change** (message struct sizes changed) — all three units must be upgraded together, same as §3.2.
- v1.5 — Fixed an OTA upload bug on all three units: `h_ota_upload()` retried `httpd_req_recv()` forever on a timeout instead of giving up, so a client aborting mid-upload could permanently wedge the httpd worker (and, since there's only one, the entire web server) until a USB reflash. Now bounded to 5 consecutive timeouts before aborting cleanly. SlaveWallas: moved `PIN_WALLAS_FB` off GPIO13 (reserved for native USB-Serial/JTAG D+, §2.4) to GPIO18.
